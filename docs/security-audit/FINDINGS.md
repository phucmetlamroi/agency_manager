### [ID: HT-001] postinstall chạy `prisma db push --accept-data-loss` mỗi lần install → nguy cơ MẤT DỮ LIỆU prod
- **Mức độ:** High
- **OWASP:** A05:2021 Security Misconfiguration (data integrity / supply-chain)
- **Vị trí:** `package.json:10`
- **Bối cảnh:** Script tiện dev: "postinstall": "prisma generate && prisma db push --accept-data-loss".
- **Vấn đề:** postinstall là lifecycle hook npm CHẠY TỰ ĐỘNG sau MỌI `npm install`/`npm ci`. Lệnh `prisma db push --accept-data-loss` đẩy schema Prisma vào DB trỏ bởi DATABASE_URL và CHẤP NHẬN mất dữ liệu (drop cột/bảng để khớp schema). Nếu install chạy ở môi trường build/CI/deploy có DATABASE_URL trỏ prod (hoặc dev thao tác nhầm env) → tự động biến đổi schema prod + có thể xoá dữ liệu, KHÔNG qua review migration. Mâu thuẫn trực tiếp quy tắc repo "chỉ THÊM model; DDL phá hủy chỉ SAU khi main deploy READY".
- **Kịch bản khai thác:** Không cần attacker — đây là "mìn" vận hành. Một lần `npm install` trên máy/CI có sẵn env prod = biến đổi/mất dữ liệu prod, khó rollback.
- **Ảnh hưởng:** Mất dữ liệu prod, downtime, rủi ro không phục hồi được. Rủi ro cao nhất về data-integrity của toàn repo.
- **Đề xuất sửa (CHƯA áp dụng):** Bỏ `prisma db push --accept-data-loss` khỏi postinstall — chỉ giữ `prisma generate`. Việc đồng bộ schema chuyển sang lệnh riêng chạy thủ công có kiểm soát (dev: `npm run db:push`; prod: migrate deploy có review). Đảm bảo pipeline build/deploy KHÔNG BAO GIỜ tự push với --accept-data-loss.
- **Rủi ro khi sửa / re-test:** Dev quen `npm install` tự tạo schema local sẽ phải chạy `prisma db push` thủ công lần đầu — ghi rõ trong README. Không ảnh hưởng runtime app.

### [ID: HT-003] startImpersonation: target-role guard is profile-local, but impersonation session is app-wide → cross-tenant escalation to another profile's OWNER/ADMIN
- **Mức độ:** High
- **OWASP:** A01:2021 Broken Access Control
- **Vị trí:** `src/actions/impersonation-actions.ts:31`
- **Bối cảnh:** startImpersonation(targetUserId, workspaceId) requires the caller to be workspace ADMIN and blocks impersonating a target who is OWNER/ADMIN — but ONLY within THIS workspace's profile: targetMember.role is the WorkspaceMember row in `workspaceId`, and targetPa is ProfileAccess for `ws.profileId` (lines 18-44). The global User.role check (line 58) only blocks the legacy super-admin. createImpersonationSession (src/lib/auth.ts:76) then overwrites the `session` cookie with the FULL targetUser object app-wide — impersonation is NOT scoped to workspaceId.
- **Vấn đề:** The rank-escalation guard resolves the target's privilege level exclusively against the current workspace's profile. It never checks whether the target holds OWNER/ADMIN ProfileAccess in ANY OTHER profile. Because the minted impersonation session is a global cookie (not workspace-bound), the impersonator inherits the target's identity everywhere, including tenants where the target is privileged.
- **Kịch bản khai thác:** Attacker A is a workspace ADMIN of workspace W in profile P_A (e.g. an explicit WorkspaceMember ADMIN row, or profile ADMIN of a workspace created after grant). Victim V runs their own org profile P_B as OWNER, and has separately accepted an invite into W as a plain MEMBER (WorkspaceMember role=MEMBER, ProfileAccess(USER) in P_A). A calls startImpersonation(V.id, W): targetMember.role='MEMBER', targetPa.role='USER' in P_A, targetUser.role='USER' → all guards pass. A's session cookie is now V. A navigates to any workspace of P_B; verifyWorkspaceAccess reads ProfileAccess(V, P_B)='OWNER' → grants OWNER. A can now transferProfileOwnership, mint admins, read P_B finance/jobPriceUSD, or evict V — full takeover of an unrelated tenant.
- **Ảnh hưởng:** Cross-tenant account takeover: a workspace ADMIN of one profile gains OWNER-level control of any other profile in which an overlapping member is privileged. Reachable whenever a multi-org user (freelancer/agency owner) is also a member of the attacker's workspace — a normal SaaS overlap.
- **Đề xuất sửa (CHƯA áp dụng):** In startImpersonation, after resolving targetUserId, reject if the target holds any OWNER/ADMIN ProfileAccess in a profile OTHER than the current workspace's profile (e.g. prisma.profileAccess.findFirst({ where: { userId: targetUserId, role: { in: ['OWNER','ADMIN'] }, NOT: { profileId: ws.profileId } } }) → throw). Alternatively, make the impersonated session workspace/profile-scoped and have verifyWorkspaceAccess refuse impersonated sessions outside the originating profile.
- **Rủi ro khi sửa / re-test:** Low. Adds one indexed query and only blocks impersonating cross-tenant-privileged users, which is the intended safe direction; legitimate same-profile impersonation is unaffected.
- **Phát hiện bởi:** AZ2 | **Xác minh bởi:** verifier độc lập | **Pass:** 1 / Lens-1 Component


### [ID: HT-004] Impersonation of a cross-team member who owns another profile → full OWNER takeover of that other tenant
- **Mức độ:** High
- **OWASP:** A01:2021 Broken Access Control
- **Vị trí:** `src/actions/impersonation-actions.ts:41`
- **Bối cảnh:** startImpersonation() lets a workspace ADMIN impersonate a target. The escalation guard (lines 31-44) resolves the target's role ONLY within the CURRENT workspace's profile: it reads targetMember.role (WorkspaceMember of this workspace) and targetPa = profileAccess for `ws.profileId` (this workspace's profile). It blocks impersonating an OWNER/ADMIN *of this profile*, but never checks whether the target is OWNER (or ADMIN) of a DIFFERENT profile. Once impersonating, the session principal becomes the victim (createImpersonationSession copies targetUser, auth.ts:85-91) and every profile-scoped action authorizes purely on getProfileRole(session.user.id, profileId) with session.user.id == victim (profile-member-actions.ts changeProfileRoleAction:245, transferProfileOwnershipAction:310, inviteToProfileAction:123). isImpersonating only blocks changePassword, nothing else.
- **Vấn đề:** The impersonation role-rank guard is scoped to the current workspace's profile only. A victim who is a mere MEMBER in the attacker's workspace but OWNER of their own separate profile B can be impersonated, and the impersonator then wields the victim's OWNER authority over profile B (mint admins, transfer ownership, remove members) with no further check.
- **Kịch bản khai thác:** 1) Attacker is profile ADMIN of profile A, workspace W. 2) Victim V owns profile B and, via the cross-team 'du học' feature, holds ProfileAccess to A and a WorkspaceMember row in W (cross-team-actions.ts approveCrossTeamAccess + task-assignment ensureWorkspaceMembership mint the WorkspaceMember row). 3) Attacker calls startImpersonation(V.id, W): targetMember exists, targetPa for A is USER (not OWNER/ADMIN), so both guards pass. 4) Now acting as V, attacker calls transferProfileOwnershipAction(profileB, attackerControlledUser) or changeProfileRoleAction(profileB, someUser, 'ADMIN') — authorized because getProfileRole(V, profileB) === 'OWNER'. Full takeover of tenant B by a user who has no legitimate role in B at all.
- **Ảnh hưởng:** Cross-tenant vertical escalation to OWNER of an unrelated profile: mint/demote admins, transfer ownership away from the true owner, remove members, and (as OWNER via verifyWorkspaceAccess) read finance/jobPriceUSD and payroll of tenant B. Single-action full compromise of another customer's workspace in this multi-tenant SaaS.
- **Đề xuất sửa (CHƯA áp dụng):** In startImpersonation, after resolving the target, reject impersonation if the target holds an OWNER (and ideally ADMIN) ProfileAccess in ANY profile other than the current one, OR — cleaner — forbid all profile-switching / profile-scoped mutations while isImpersonating (the impersonation banner is for read-only support use). At minimum, gate profile-member-actions.ts (changeProfileRole/transferOwnership/inviteToProfile/removeFromProfile) to reject when session.user.isImpersonating is true, mirroring the changePassword isImpersonating block.
- **Rủi ro khi sửa / re-test:** Low. Blocking profile-scoped mutations during impersonation only removes an unintended capability; legitimate support-impersonation is for viewing a user's own-profile experience, not administering other tenants. Adding a cross-profile OWNER pre-check is a read + comparison with no schema change.
- **Phát hiện bởi:** V-ESCALATION | **Xác minh bởi:** verifier độc lập | **Pass:** 1 / Lens-1 Component


### [ID: HT-005] voidInvoice: TOCTOU double-refund of client deposit (non-idempotent increment)
- **Mức độ:** High
- **OWASP:** A04:2021 - Insecure Design (Business-logic race / TOCTOU)
- **Vị trí:** `src/actions/invoice-actions.ts:594`
- **Bối cảnh:** voidInvoice() reads the invoice and guards `if (invoice.status === 'VOID') return already void` at line 574 — OUTSIDE the transaction. Inside the $transaction (line 577) it (1) sets status=VOID with an UNCONDITIONAL `tx.invoice.update where:{id}` (no status predicate, line 579), and (2) refunds the deposit with a blind `tx.client.update({ data:{ depositBalance:{ increment: invoice.depositDeducted } } })` (line 594-601). There is no advisory lock and no conditional status flip / affected-rows assertion — unlike createInvoiceRecord which correctly uses an atomic `updateMany where UNBILLED` + count check.
- **Vấn đề:** The 'already void' check and the refund write are not atomic. The in-transaction status update is unconditional, so it cannot act as an optimistic guard. Postgres row locking serializes the two `increment` operations but does NOT dedupe them — both `+= depositDeducted` still apply. depositBalance is real money: it is later consumed by createInvoiceRecord (clientDepositDeducted → reduces totalDue), so inflating it makes the agency under-bill the client.
- **Kịch bản khai thác:** voidInvoice is an exported Server Action (a public POST endpoint, callable directly bypassing UI). A finance user double-clicking 'Void', or two concurrent POSTs with the same invoiceId, both read status='SENT', both pass the line-574 guard, both enter the transaction, both set status=VOID (idempotent) and both run `depositBalance += invoice.depositDeducted`. Net result: the client's deposit is credited twice (or N times for N concurrent calls) for a single void. Repeat the void→refund→re-invoice cycle to arbitrarily inflate depositBalance.
- **Ảnh hưởng:** Client deposit balance inflated by an unbounded multiple of the real refund, causing the agency to under-bill (lose revenue) on subsequent invoices. Triggerable accidentally by a normal double-click; no malicious intent required.
- **Đề xuất sửa (CHƯA áp dụng):** Make the void atomic and idempotent: inside the transaction do `const claimed = await tx.invoice.updateMany({ where:{ id: invoiceId, status:{ not:'VOID' } }, data:{ status:'VOID' } })` and `if (claimed.count === 0) return` BEFORE the deposit increment and task revert, so only the single winning transaction performs the refund. Optionally take `pg_advisory_xact_lock(hashtextextended(invoiceId,0))` at the top of the tx (the same pattern already used in src/lib/review/*).
- **Rủi ro khi sửa / re-test:** Low. The refund and task-revert become guarded by the affected-row count; legitimate single voids are unaffected. No schema change.
- **Phát hiện bởi:** V-RACE | **Xác minh bởi:** verifier độc lập | **Pass:** 1 / Lens-1 Component
