# Signup failure on self-hosted production — 2026-09-17

## Confirmed evidence

- `GET https://hustlytasker.xyz/signup` returns 200, served by Nginx/Ubuntu with Next.js.
- The live `main-app-2d5c0601290a99b7.js` initializes BotID unconditionally for `POST /api/auth/signup`.
- The BotID challenge script at `/149e9513-01fa-4fb0-aad4-566afd725d1b/2d206a39-8ed7-437e-a3be-862e0f06eea3/a-4-a/c.js?i=0&v=3&h=hustlytasker.xyz` returns **404 HTML**.
- A direct diagnostic POST with only `{ "acceptTos": false }` returns **400 JSON** with the expected terms-validation message. The API is reachable. This request cannot create an account or send email.
- The installed BotID 1.5.11 client wraps `window.fetch` and awaits that challenge script before sending the protected request. Script loading failure rejects the request before the original fetch runs.
- The live signup page catches every thrown error with “Không thể kết nối đến máy chủ.” This also mislabels JSON parsing errors from HTML proxy responses.

These observations identify a stale BotID client integration as a blocker for the reported signup flow. The server SDK also requires Vercel OIDC/request context in production, so a client-only fix is insufficient. See [Vercel's BotID setup requirements](https://vercel.com/docs/botid/get-started).

## Patch

The workspace already contained an undeployed self-hosting patch in `next.config.ts`, `src/instrumentation-client.ts`, and `src/actions/signup-actions.ts`. This fix preserves that work and completes its checks:

- Enable BotID rewrites, browser instrumentation, and server verification consistently only when `VERCEL === '1'` and Electron is disabled.
- Keep honeypot, email/password checks and Upstash rate limits in the signup flow. Vercel deployments continue to enforce BotID.
- Handle malformed/HTML responses separately from failed fetches. Preserve validation and rate-limit messages.
- Add `npm run test:signup`: 19 isolated regression tests. External services, account writes and email delivery are mocked.

Validation: all 19 tests passed; full-project TypeScript checking passed; ESLint passed for the five affected TypeScript files. Linting the `.mjs` test file hits an existing ESLint configuration issue (`@typescript-eslint/no-unused-vars` enabled without its plugin for JavaScript files); the test file itself executes successfully under Node's test runner.

## Deployment and remaining verification

The live site still serves the old client bundle. Deploying requires a **fresh Next.js build**, not merely restarting the old build: `NEXT_PUBLIC_BOTID_ENABLED` is embedded in browser JavaScript at build time. For the self-hosted release, leave `VERCEL` unset and follow the existing `deploy/digitalocean/README.md` release process. No database schema change is involved.

After deployment, verify the browser no longer requests the BotID challenge on signup and complete signup/email verification with a controlled test inbox. A real production account and actual email delivery have not been tested in this investigation.
