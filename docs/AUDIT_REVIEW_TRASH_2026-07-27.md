## CAO

### `src/lib/review/folder-scope.ts:56`
**Editor folder-scope collapses to the whole workspace because the auto-upload chain stamps createdById on the ROOT and CLIENT folders**

- **Vì sao:** Adjacent to the trash lens but found in the same resolution code, and it is a live authorization bypass. `getFolderScope` adds every folder the user created to `allowedPrefixes` (56-59). The auto-chain sets `createdById` to the UPLOADING EDITOR at all four levels — task-folder.ts:91 (root), :101 (client), upload-service.ts:99 (ensureRootFolder) and folders.ts:163 (ensureWorkspaceRoot). Once an editor's own root path '/{rootId}/' is in the set, dedupePrefixes (71-76) drops every other prefix and isPathMutable (85-88) returns true for every path in the workspace, since all paths start with '/{rootId}/'.
- **Kịch bản hỏng:** Editor A is the first person to upload (or to click 'Thư mục mới') in a fresh month workspace, so the root ReviewFolder is created with createdById = A. From then on A is a non-admin whose FR-03 scope is workspace-wide: getFolderTree/listChildren show every other editor's deliverables, and assertAssetInScope / assertVersionInScope / assertFolderPathsMutable all pass, so A can rename, move, delete, download originals and mint Mux playback tokens for every other editor's client footage in that workspace. The same over-grant happens one level down for the CLIENT folder even when A did not create the root.
- **Hướng sửa:** Do not attribute machine-created folders to the triggering user: pass `createdById: null` for rows that carry a systemKey (task-folder.ts:91/101/113, upload-service.ts:99, folders.ts:163) — the schema already documents `createdById String? // null = system (auto-folder)`. Belt-and-braces: exclude `systemKey != null` rows from the ownFolders query at 56-59, since FR-B07's creator-only delete rule should also not apply to system folders.

### `src/lib/review/folder-scope.ts:57`
**Auto-created workspace ROOT counts as an editor's "own folder" → workspace-wide write scope + whole-tree delete**

- **Vì sao:** getFolderScope adds every folder whose createdById is the caller to allowedPrefixes (line 57, merged at 65). The workspace root is created with the *editor's* id: ensureRootFolder passes createdById: userId (upload-service.ts:99), and ensureTaskFolderPath forwards access.userId into ensureFolder for the root level (task-folder.ts:51, called at upload-service.ts:687); folders.ts:163 does the same. So the first member to upload in a fresh workspace ends up with allowedPrefixes = ["/{rootId}/"], which dedupePrefixes collapses everything else into. isPathVisible/isPathMutable then return true for every path in the workspace, so FR-03 folder scoping is fully defeated for that user — and deleteItems' FR-B07 creator check (folders.ts:771-776) also passes on the root because createdById === userId. System-created rows are being treated as user-authored rows.
- **Kịch bản hỏng:** Fresh month workspace. Editor E (role USER, not admin, assigned to one task) hands off the first deliverable from the task drawer. ensureTaskFolderPath creates root + client folder with createdById = E. E's scope is now the whole tree. E calls POST /api/review/items/delete with {type:'folder', id: <rootId>}: the creator check passes, assertFolderPathsMutable passes, and deleteItems' subtree sweep (folders.ts:800-814) soft-deletes every folder, asset and version in the workspace under one batchId. Short of that, E can already read, rename, move and delete every asset in the workspace, including other editors' work.
- **Hướng sửa:** Exclude system rows from the ownFolders prefix source: `where: { workspaceId, createdById: userId, systemKey: null }`. Better still, stop attributing auto-chain folders to a user at all — pass createdById: null for the root/client/brand levels in ensureTaskFolderPath (task-folder.ts:86-102) and ensureRootFolder (upload-service.ts:99), since those rows are system-owned.

### `src/lib/review/folders.ts:985`
**`orphanedFromPurge` is never cleared, so a re-homed folder is permanently un-restorable in the UI while the purge destroys its whole subtree anyway**

- **Vì sao:** restoreItems sets `orphanedFromPurge: movedToRoot` when a folder is re-homed to the workspace root (folders.ts:985) and `orphanedFromPurge: true` for a re-homed asset (folders.ts:1011). Nothing anywhere in src/ or prisma/ ever sets it back to false (verified: the only writes are those two lines plus the schema default at schema.prisma:1664/1700). listTrash then exports `restorable: !f.orphanedFromPurge` (folders.ts:890) and TeamTrash.tsx:502/532 renders the Restore control `disabled` with the tooltip "Không thể khôi phục (thư mục gốc đã bị xóa vĩnh viễn)" — which is now false: the folder is perfectly restorable, the flag is just stale from a previous restore. Critically, purgeExpiredTrash does NOT consult orphanedFromPurge at all (purge.ts:259-264) — so the item the UI refuses to let the admin restore is still destroyed on schedule. And because deleteItems stamps the whole subtree with the folder's batchId (folders.ts:805-813), none of the child assets appear as batch roots in listTrash (folders.ts:868-871), so they cannot be restored individually either. The entire subtree is unrecoverable-by-UI and then auto-destroyed.
- **Kịch bản hỏng:** Folder F is restored once at a time when its parent was gone, so it lands at the workspace root with orphanedFromPurge=true (folders.ts:985). Months later staff trash F again, now holding 40 delivered videos. In Recently Deleted, F shows with Restore greyed out and a misleading tooltip. Its 40 assets are not listed (they share F's batchId, so they are not batch roots). Nothing in the product can bring them back. Thirty days later the cron's asset step (purge.ts:241-246) purges all 40 assets — Mux assets and R2 originals deleted — because that step never looks at orphanedFromPurge.
- **Hướng sửa:** Clear the flag on every successful restore (set `orphanedFromPurge: false` in the `clear` object at folders.ts:951 and folders.ts:999, not only in the re-home branch). Independently, make the flag advisory-only: `restorable` should be computed from whether a valid landing folder exists right now (the workspace root always does), never from a historical marker — and the purge should refuse to destroy anything the UI is currently refusing to let the user restore.

### `src/lib/review/folders.ts:949`
**restoreItems has no nested-selection guard, so bulk-restoring a parent and child together can rip the child out to the root and permanently flag it un-restorable**

- **Vì sao:** The folder loop iterates `folderRows` in arbitrary DB order — no depth/path sort, and no `nestedFolderIds` skip. Both sibling operations have that guard precisely because processing a descendant against a stale ancestor corrupts the tree: deleteItems at folders.ts:786-788 and moveItems at folders.ts:677-679. Here, whether a child is re-homed depends entirely on whether its parent happened to be processed first: folders.ts:953-954 looks up `folder.parentId` with `deletedAt: null`, so if the child is handled before the parent's `clear` commits, the parent is still trashed, the lookup returns null, and the child falls through to `target = root` (folders.ts:964) with `movedToRoot = true` — triggering the path/depth rewrite at folders.ts:982-984 and setting `orphanedFromPurge: true` at folders.ts:985, which per the finding above is never cleared. Both folders are reachable as batch roots in the trash list whenever the child was trashed in an earlier batch than the parent (listTrash's root rule, folders.ts:862-866), and TeamTrash's bulk restore sends them in one call.
- **Kịch bản hỏng:** Staff trash subfolder C (batch B1). A week later they trash its parent P (batch B2) — deleteItems' subtree sweep only touches `deletedAt: null` rows (folders.ts:800-801), so C keeps B1 and therefore still qualifies as a batch root. Recently Deleted lists both P and C. Admin selects both and clicks bulk Restore. C is returned first by the DB, its parent P is still deleted, so C is re-homed to the workspace root and stamped orphanedFromPurge=true. P is then restored in place, empty. The admin's folder structure is silently flattened, and C can never be restored again if it is ever re-trashed.
- **Hướng sửa:** Mirror deleteItems/moveItems: sort folderRows by `depth` ascending (or by path length) so ancestors are always restored first, and skip any selected folder nested under another selected folder — its ancestor's restore already covers it. Only re-home a folder whose parent is genuinely absent after all selected ancestors have been processed.

### `src/lib/review/folders.ts:932`
**Bulk restore is row-order dependent: restoring a trashed parent together with a separately-batched trashed child scatters the child to the workspace root**

- **Vì sao:** `folderRows` is fetched with no `orderBy`, so Postgres returns the selected trash roots in arbitrary (heap/index) order, and the loop at line 949 processes them in that order. The landing-zone decision at line 954 depends on whether the parent is live AT THAT MOMENT inside the same transaction. If the descendant is processed first its parent is still trashed → it is re-homed to root, its whole subtree path is rewritten (line 982), `parentId` is repointed and `orphanedFromPurge` is set true (line 985). If the ancestor happens to be processed first, the child restores into its real parent. Same input, two different trees, decided by DB row order. This combination is reachable and normal: delete a child folder, then later delete its parent — the parent's sweep at folders.ts:800 only touches `deletedAt: null` rows, so the child keeps its own earlier deleteBatchId and listTrash lists BOTH as roots (folders.ts:862), which is precisely what "Chọn tất cả" then selects.
- **Kịch bản hỏng:** Admin deletes folder "Video A" on Monday (batch1). On Tuesday deletes its parent "ForTesting" (batch2 — the sweep skips already-deleted Video A). Trash lists both rows. Admin clicks Chọn tất cả → Khôi phục (2). If findMany returns Video A before ForTesting, Video A is re-homed to the workspace root as a top-level sibling of ForTesting, permanently marked orphanedFromPurge=true, and ForTesting comes back empty. The toast reports "(1 mục về gốc … vì thư mục gốc đã bị xóa)" even though the parent was restored microseconds later in the same transaction. The admin's folder hierarchy is silently flattened.
- **Hướng sửa:** Order the folder work deterministically shallowest-first before the loop: `folderRows.sort((a, b) => a.path.split('/').length - b.path.split('/').length || a.path.localeCompare(b.path))` (or add `orderBy: [{ depth: 'asc' }, { path: 'asc' }]` to the findMany at line 932). Then a selected ancestor is always restored before its selected descendant, and the descendant's parent-liveness probe sees the restored parent.

### `src/lib/review/folders.ts:941`
**listTrash and restoreItems apply no folder-scope and no creator/admin check, while deleteItems enforces both**

- **Vì sao:** deleteItems runs the FR-B07 creator-or-admin rule (folders.ts:771-776) and `assertFolderPathsMutable` against the caller's folder scope (folders.ts:778-779). listTrash (line 844) and restoreItems (line 941) each call only `requireReviewAccess({ workspaceId })` and never touch getFolderScope — grep shows no getFolderScope call anywhere between lines 839 and 1021. So any workspace member, including a folder-scoped editor whom FR-03 confines to one assigned subtree, gets the full name list of every trashed folder and asset in the workspace and can restore any of them. Restore is not a read-only undo: it repoints `parentId`, rewrites the subtree's materialized `path` and `depth` (line 982-985), and can relocate a whole subtree to the workspace root — a structural mutation outside the caller's permitted scope.
- **Kịch bản hỏng:** A folder-scoped editor assigned only to /root/ClientA/ opens /team/trash. The list shows every deleted folder in the workspace, including ClientB's, with names, sizes and who deleted them (FR-03 information leak). - **Hướng sửa:** In listTrash, load the caller's scope and filter rootFolders/rootAssets by `isPathVisible` on the row's path (the folder rows already carry `path`; join the asset's folder path). ### `src/lib/review/folders.ts:941`
**restoreItems performs no folder-scope or creator authorization — asymmetric with deleteItems**

- **Vì sao:** restoreItems only calls requireReviewAccess({ workspaceId }). deleteItems, on the same rows, enforces the FR-B07 creator-only rule for non-admins (771-776) and assertFolderPathsMutable (779). Restore enforces neither, yet it is a structural mutation: it rewrites parentId/path/depth for a whole subtree (978-986), sets orphanedFromPurge, and moves ancestor byte rollups (991-992).
- **Kịch bản hỏng:** A folder-scoped editor who cannot even see folder X (isPathVisible false) POSTs /api/review/trash/restore with X's id — ids leak through the activity feed, share items and the admin trash page. X is restored, and because its original parent is gone it is silently re-homed to the workspace root with the whole subtree's paths rewritten: an out-of-scope structural mutation by a user with no rights over X, and one that also undoes an admin's deliberate delete.
- **Hướng sửa:** Mirror deleteItems: compute getFolderScope, run assertFolderPathsMutable over the restored rows' paths, and apply the creator-or-admin rule for folders before clearing deletedAt.

### `src/lib/review/parse-task-context.ts:19`
**parseVideoTitle treats any ASCII hyphen as the client/video separator, so ordinary titles silently mint a bogus client folder — and `matched=true` suppresses the warning exactly there**

- **Vì sao:** `TITLE_RE = /^([^/·]+?)\s*(?:\/\s*([^·]+?))?\s*[·\-]\s*(.+)$/` makes the separator class `[·\-]` — ASCII hyphen included, and REQUIRED. So the regex matches any title containing a hyphen, and greedily reinterprets the text before the first hyphen as the CLIENT. `matched` is then set true (line 30), which is what drives `parsedOk` (task-assets.ts:148) and therefore whether the amber warning renders (TaskReviewUploadSection.tsx:299). The warning is thus inverted relative to risk: it fires on the SAFE path (fallback to the task's real client) and stays silent on the DANGEROUS path (a title fragment promoted to a client). Downstream, `parsed.client` becomes the client folder's display NAME (task-folder.ts:98), and when the task has no `clientId` it also becomes the folder's identity via `slugifyBrand(parsed.client)` (task-folder.ts:83) — a genuinely new top-level "client" folder. When the task DOES have a clientId, the folder is keyed correctly but permanently NAMED after the title fragment, because ensureFolder only sets `name` on create (task-folder.ts:41-53) and returns the existing name forever after (line 35).
- **Kịch bản hỏng:** Task titled "Bathroom 1 - Reel 30s", no client set. parseVideoTitle returns { client: 'Bathroom 1', brand: null, video: 'Reel 30s', matched: true }. No warning is shown. The strip reads "Lưu vào: Tháng 7/2026 / Bathroom 1 / Reel 30s" — plausible enough that nobody questions it — and a permanent top-level client folder named "Bathroom 1" (systemKey ws:{id}:client:bathroom-1) is created. Every later task whose title starts "Bathroom 1 -" files under this phantom client.
- **Hướng sửa:** Split the two separators and stop inferring a client from a hyphen: require `·` (or `|`) for the client/video split and keep `-`/`–` as ordinary characters inside the video name — `/^([^/·]+?)\s*(?:\/\s*([^·]+?))?\s*·\s*(.+)$/`. ### `src/lib/review/upload-service.ts:168`
**A folder can be trashed while an upload into it is in flight — the new asset lands live under a trashed folder**

- **Vì sao:** initiateUpload reads the folder with deletedAt:null (160-163), then creates the ReviewAsset in a separate round-trip (168-179) with no transaction and no lock. deleteItems takes no lock either and snapshots the subtree asset ids inside its tx at folders.ts:806-810, so an asset created after that read is never swept. The asymmetry is deliberate elsewhere: moveItems takes pg_advisory_xact_lock(workspaceId) (folders.ts:655) and initiateTaskUpload locks the video folder (upload-service.ts:696) — deleteItems takes neither.
- **Kịch bản hỏng:** Editor starts an upload into folder F. Admin trashes F in the window between upload-service.ts:163 and :168. The ReviewAsset is created with deletedAt=null under trashed F, misses deleteItems' sweep, and the upload runs to completion: R2 stores the object, driveCompletion emits the Mux job and the encode is billed — yet the asset never appears in /team (its parent is filtered out at folders.ts:455) and getFolder(F) 404s. It then blocks F's purge forever (purge.ts:209-215). Same window exists for the asset-target branch (196-199) and for team folder-tree creation (folders.ts:257-286).
- **Hướng sửa:** Create the asset inside a transaction that re-reads the folder with deletedAt:null under the same advisory lock, and have deleteItems acquire pg_advisory_xact_lock(hashtextextended(workspaceId,0)) the way moveItems already does at folders.ts:655.
